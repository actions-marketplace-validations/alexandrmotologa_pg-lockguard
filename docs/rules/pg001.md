# PG001: CREATE INDEX without CONCURRENTLY

## Lock Level Acquired
`SHARE` (Blocks all concurrent `INSERT`, `UPDATE`, and `DELETE` operations)

## Problem
Building an index without the `CONCURRENTLY` option locks the target table against all write traffic for the entire duration of the index build. On tables with millions of rows, an index build can take minutes or hours. During this period:
- Active transactions attempting to write to the table stall in lock-wait state.
- Database connection pools quickly reach saturation.
- Application web servers exhaust thread pools and return 504 Gateway Timeouts to users.

## Dangerous Pattern
```sql
-- Acquires SHARE lock, blocking all writes
CREATE INDEX idx_users_email ON users (email);
```

## Safe Zero-Downtime Recipe
Build the index concurrently outside an explicit transaction block:

```sql
-- Step 1: Create the index concurrently (reads and writes continue uninterrupted)
CREATE INDEX CONCURRENTLY IF NOT EXISTS idx_users_email ON users (email);
```

> Note: `CREATE INDEX CONCURRENTLY` cannot run inside an explicit transaction (`BEGIN ... COMMIT`). If using a migration runner that wraps scripts in transactions by default, disable transactions for this file.
